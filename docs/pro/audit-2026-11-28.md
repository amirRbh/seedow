# Audit de mise en production de Seedow Pro — 28 novembre 2026

Objet : dire, faits à l'appui, si Seedow Pro peut être présenté à un premier
cabinet de conseil en gestion de patrimoine (CGP), et ce qui manque.

## Verdict

**L'application publiée n'est pas présentable à un CGP aujourd'hui.** Les tables
de Seedow Pro n'existent pas dans la base de l'application publiée : toute page
`/pro` qui lit ou écrit des données échoue. La base de fonds est vide et la
précision de l'extraction n'a jamais été mesurée.

**Ce qui peut être montré dès maintenant, honnêtement présenté :** les rapports
d'exemple générés à partir de 7 annexes réelles par le vrai moteur
(`fixtures/report/sample-report.pdf`, `fixtures/report/sample-portfolio-report.pdf`).
Il faut les présenter comme une démonstration du format et des règles appliquées
sur des documents réels, pas comme un service en production.

**Délai réaliste pour présenter l'application elle-même :** atteignable une fois
les quatre actions de la section « Actions qui demandent ton intervention »
réalisées. La suite (mesure, base, parcours complet) est outillée et se lance
depuis le workflow **Pro ops**.

## 2. Pourquoi la base de fonds est vide

1. Les tables Pro n'existent pas dans la base de l'application (constat du 28/11,
   run « Pro ops » n° 3 : `pro_funds`, `pro_fund_costs`, `pro_predefined_profiles`,
   `pro_cabinets` → `404 PGRST205`, `assets` → `200`).
2. L'ingestion n'a jamais tourné : c'est un script hors ligne, aucun workflow ne
   le lançait, et les dépôts faits depuis `/pro/fonds` restaient dans `inbox/`.
3. Elle ne pouvait pas tourner : le secret `ANTHROPIC_API_KEY` est absent des
   secrets Actions du dépôt (même run).

**Correction d'une affirmation antérieure** : les migrations Pro annoncées
« appliquées en production » le 25/11 et le 28/11 l'ont été dans le projet visé
par les secrets GitHub, pas dans celui de l'application. Elles y sont saines
(RLS active sur les 11 tables, API REST qui les voit), mais l'application ne les
utilise pas.

## 3. Sécurité et isolation des cabinets

Vérifié sur Postgres 16 (`scripts/pro/test-migration.sh`, stub Supabase) — **pas
encore sur la base de l'application**, où les tables n'existent pas :

- un cabinet ne voit ni les clients, ni les rapports, ni les PDF, ni les fiches
  de recueil, ni les profils prédéfinis, ni les dépôts d'un autre ;
- un utilisateur ne peut écrire ni dans un autre cabinet, ni dans les tables de
  fonds, ni de rapport, ni de fiche (réservés au serveur) ;
- rapports et fiches de recueil : ni modification ni suppression, y compris par
  le rôle serveur ;
- `client_ref` refuse un e-mail (pseudonyme seulement, RGPD) ;
- frais (`pro_fund_costs`) : insertion seule, preuve obligatoire en `auto`, même
  KID importé une seule fois ; journal des imports illisible par les utilisateurs.

Le test de bout en bout (`e2e`) refait le contrôle d'isolation sur l'application
publiée avec deux comptes de test : il n'a pas encore pu tourner.

## 5. Validation de l'IA (phase 3)

**Non mesurée : bloquée par l'absence du secret `ANTHROPIC_API_KEY`.** Aucun
chiffre de précision ne doit être annoncé à un CGP avant la mesure.

Ce qui est prêt :

- les 7 annexes réelles de `fixtures/annexes/` et leur jeu de référence saisi à
  la main, indépendamment du modèle : 11 champs de durabilité par annexe, plus un
  bloc d'identité ajouté le 28/11 ;
- constat sur l'identité : **aucune des 7 annexes ne mentionne d'ISIN** (attendu
  `null` : l'ISIN vient de GECO, jamais de l'extraction) ; les 7 LEI sont relevés
  tels quels, clés ISO 17442 vérifiées ; la société de gestion n'est jamais
  désignée explicitement ;
- notation par champ, et décompte des valeurs « inventées » (données alors que
  le document ne les énonce pas) ;
- tâche `eval` du workflow, plafonnée (10 $ par défaut).

Champs demandés et leur source réelle :

| Champ              | Source fiable                                                                                         | Mesure prévue                                             |
| ------------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| ISIN               | GECO (AMF) ou manifeste, jamais l'annexe                                                              | l'extraction ne doit rien inventer                        |
| Nom du fonds       | GECO ; l'annexe le confirme                                                                           | précision par libellé normalisé                           |
| Société de gestion | GECO (l'annexe ne la nomme pas)                                                                       | l'extraction ne doit rien inventer                        |

| Frais              | **KID / DIC, pas l'annexe** : lus par le parseur déterministe existant, sans IA, page et ligne citées | tests du parseur ; mesure sur KID réels au premier import |

## 6. Base de fonds (phase 4)

Prête, non exécutée sur la base de l'application.

- **Liste de départ** : 168 fonds, 68 sociétés de gestion (`data/pro/uc-universe-v1.json`),
  tirés par règles mécaniques de l'extrait GECO du 9/10/2026 (fonds de droit
  français, ouverts à tous souscripteurs, au nom portant un terme ESMA, au plus 4
  par société). La liste ne vaut pas classement.
- **Schéma** (migration additive `20261128120000_pro_fund_reference.sql`) :
  provenance de l'identité, pages d'origine des annexes, frais avec preuve,
  journal des imports. Doublons empêchés par ISIN, empreinte SHA-256 des
  documents et `(isin, empreinte)` pour les frais.
- **Import** (`scripts/pro/build-fund-base.ts`) : GECO → identité, KID → frais,
  prospectus → annexe isolée, puis extraction. Préparation sans écriture par
  défaut, écriture sur confirmation explicite.
- **Sources et licences** : GECO (AMF) et documents réglementaires publics
  (KID, prospectus). Conditions de réutilisation commerciale **à confirmer par
  écrit**. Aucune donnée MSCI ou d'un fournisseur sous licence.
- **Limite** : GECO ne couvre que les fonds agréés en France ; les SICAV
  luxembourgeoises, fréquentes en unités de compte, exigent une autre source.

## 11. Actions qui demandent ton intervention

1. **Créer le secret `ANTHROPIC_API_KEY`** dans GitHub : Settings → Secrets and
   variables → Actions → New repository secret. Le run `status` confirmera sa
   présence et sa validité, sans jamais afficher sa valeur.
2. **Appliquer les 4 migrations Pro dans Lovable Cloud** (base de l'application),
   dans cet ordre, en demandant à Lovable de les exécuter telles quelles :
   `20261124120000_pro_sustainability_adequacy.sql`,
   `20261124130000_pro_annex_inbox_privacy.sql`,
   `20261125120000_pro_collection_modes.sql`,
   `20261128120000_pro_fund_reference.sql`.
   Lovable régénère ensuite `src/integrations/supabase/types.ts`.
3. **Décider du rôle du second projet Supabase** (celui des secrets GitHub) :
   - soit c'est un environnement de test : le garder, et ajouter des secrets
     qui visent l'application (URL, clé `service_role`, chaîne de connexion),
     si Lovable Cloud les fournit ;
   - soit c'est un reste : le dire, et les workflows B2C d'ingestion sont à
     revoir aussi.
4. **Puis me laisser lancer**, dans l'ordre : `eval` (plafond 10 $),
   `fund-base` sur 20 fonds (plafond 25 $), `e2e`, et enfin la base complète.
5. Avant le pilote : invitation obligatoire pour `/pro` (A6), CGU Pro, contrat de
   traitement RGPD, confirmation des conditions de réutilisation GECO (A10).
